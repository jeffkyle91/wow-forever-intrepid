# Addon tools

The tools for working on the addon. Python 3.9 or newer, standard library only; nothing here talks to the internet.

| Tool | What it does |
| --- | --- |
| `exchange_fixtures.py` | Builds and checks the exchange-string test files in `docs/spec/fixtures/`, and writes the addon's self-test sample (`IntrepidManager/core/SelfTestSamples.lua`). |
| `synthetic.py` | Invented nights and awards strings for practice and for the tests. |
| `api_lint.py`, `api-known.json`, `api-widgets.json` | The list of the game's API names we have evidence for, and the check that the addon uses only those (below). |
| `measured_fonts.py` | Writes `tests/support/measured_fonts.lua` from a `/im facts` result. |
| `make-probe-items.py` | Writes `IntrepidProbe/Items.lua` from `data/loot/*.json`. |
| `make-paste-tests.py` | Writes the paste-test files the probe's `/ip paste` checks. |

The tools that copy builds to a tester's own PCs, and the test results they bring back, stay out of this repository: the results hold real character names.

## API names: `api_lint.py` and `api-known.json`

The game is out of reach between test sessions, and a call to a name the client does not have is an error a player meets mid-raid. `tools/api-known.json` is the list of client names the addon may use: **present** (with the source of the evidence), **absent** (the client lacks it; the probe saw that) and **unverified** (used without evidence; each carries the reason). Sources: `probe` (IntrepidProbe results from the beta), `selftest` (`/im selftest` results), `fl` (ForeverLoot's shipped code, which was written for this client: "very likely", not proof). CI runs `check` and `selftest`.

```
python3 -B tools/api_lint.py check       # lint IntrepidManager/ and the client globals in .luacheckrc
python3 -B tools/api_lint.py selftest    # test the tool and the list itself
```

`check` looks at method calls (`obj:Name()`), members of listed namespaces (`C_PartyInfo.GetLootMethod`, `Enum.LootMethod.Group`), events given to `RegisterEvent`, frame types and templates given to `CreateFrame`, font objects given to `CreateFontString`, and the globals in `.luacheckrc`. It cannot see the type of a variable (a real method on the wrong widget type), arguments, or names built at run time (it counts those). A file that declares a local with a namespace's name (`local Settings = FL.Settings`) is not checked for that name.

**When `check` fails on a name you need**
- If you have evidence, add it with its source: `python3 tools/api_lint.py add --kind methods --source fl SetPoint` (kinds: `globals`, `namespaces` with `--ns C_PartyInfo`, `events`, `frame_types`, `templates`, `fonts`, `methods`).
- If you have none, say so: `python3 tools/api_lint.py add --kind methods --unverified "documented, never run in the game; test it in the next session" SetUserPlaced`. `check` then passes and prints the name as a to-do, so it ends up on the next game session's list.
- If the name is listed as absent, the client does not have it; use the replacement (for example `C_Item.GetItemInfo` for `GetItemInfo`).

**After a game session with a new probe or self-test run**
```
python3 -B tools/api_lint.py facts path/to/IntrepidProbe.lua path/to/IntrepidManager.lua
```
reads only API names and yes or no from those saved variables (never player data), moves what the client now says into `present` or `absent`, and turns runs that disagree into `unverified`. Look at `git diff tools/api-known.json` before committing. It reads the saved variables of `/im facts` too (source `facts`: the methods the game lists for its widget types, the fonts and the templates it accepted).

```
python3 -B tools/api_lint.py widgets path/to/IntrepidManager.lua      # tools/api-widgets.json: the methods of each widget type
python3 -B tools/measured_fonts.py path/to/IntrepidManager.lua --write # tests/support/measured_fonts.lua: the fonts the pictures measure with
```

`tools/api-widgets.json` holds, for each kind of widget the game was asked about (Frame, Button, CheckButton, EditBox, ScrollFrame, Slider, StatusBar, FontString, Texture), every method the game lists for it (measured by `/im facts` through the widget's metatable). The strict stand-ins use it: `SetText` on a plain frame raises there, as it would in the game, even though `SetText` is on the known-good list for buttons. `tests/support/measured_fonts.lua` is the same kind of data for fonts: size, file, color, line height and the advance of every printable character, which `tests/support/metrics.lua` sums to estimate how wide text is.

**To read another addon for names**
```
python3 -B tools/api_lint.py collect path/to/Addon --exclude Libs --defs path/to/Addon/Libs --luacheck --source fl --merge
```
lists what that addon calls (leave off `--merge` to only look). Names the addon defines itself are left out, and so are names you pass in `--ignore`. Check the result by hand: a name that an addon only uses behind an existence test (`if Thing then`) proves nothing, and `unverified` is the honest place for it.

The strict stand-in widgets for window tests are in `tests/support/strict_ui.lua`; they judge by the same list (`tests/strict_ui_test.lua` shows how to use them).

## Window pictures: `tests/storyboards.lua`

The game is not at hand while windows are written, so every window gets a storyboard in `tests/storyboards/`: a script that builds the window from the strict stand-in widgets, presses its buttons with `game.fire`, and takes a picture with `story.snap("caption")` at each step.

```
lua5.1 tests/storyboards.lua            # every storyboard
lua5.1 tests/storyboards.lua demo       # the named ones
```

The pictures are written to `build/pictures/` (not kept in git): `index.html` with all of them, one page per picture, and `artifact.html`, the same page without the document around it, for the Artifact tool. CI runs the storyboards and keeps `build/pictures` as the `window-pictures` artifact of the run, so a reviewer can look at a window without running anything. A storyboard that raises an error fails the run, which also tells us that a window no longer builds.

**What a picture is:** HTML drawn from what the widgets say (anchors, sizes, text, colors, textures, states), placed by the game's anchoring rules (`tests/support/layout.lua`). **What it is not:** the game. Text widths are estimates (`tests/support/metrics.lua`), fonts and Blizzard's art are approximated in CSS, item icons are placeholders, and the parts of the stock templates (title text, close button, inset) are guesses (`tests/support/stock_templates.lua`). The notes under a picture say what to check (a window partly off the screen, a widget that has no anchor) and which guesses it relied on. The first look at the real thing is in the game; the in-game test mode is to report the real template parts so the guesses can be corrected.

`tests/storyboards/session.lua` is the storyboard of the loot session window and shows how one is written: it builds the window from the addon's real files (`IntrepidManager/ui/`), feeds it the sample view-model of `IntrepidManager/ui/Sample.lua`, presses its buttons with `game.fire`, and takes a picture at each step (compact, a list of 40 scrolled, the confirmation, the banners, the picker, roomy, and the flat frame).


`tests/storyboards/import.lua` (the import window) shows time and pasting. `game.paste(editBox, text)` is a player pasting into a box that has the keyboard focus (it runs `OnTextChanged` the way typing does, and honors `SetMaxLetters`). `game.advance(seconds)` lets time pass and runs the `C_Timer.After` callbacks that fall due: nothing runs by itself in the stand-ins. `GetServerTime()` and `date()` read the stand-in's clock, in UTC, so a test gives the same answer in every time zone. `UI.new({ setTextFires = true })` makes `SetText` on an edit box run `OnTextChanged` too, which the game is believed to do; the import window's tests run both ways. A multi-line edit box wraps its text at its width less its insets and cuts a word that is too long where it overflows, which is how the game is believed to wrap a string with no spaces in it.

## Trying the windows in the game: `/im window` and `/im facts`

`/im window [session, import, picker or confirm] [roomy] [flat]` opens the real windows on sample data (invented names; nothing is given or imported), to look at them in the game before the engine exists. `/im facts [label]` opens all of them, measures what the game's own widgets really are (which methods each widget type has, the parts and sizes of the stock templates, each font's size and the width of every character, how a multi-line edit box in a scroll frame grows and what events it fires, the width of every label in the windows against its box) and keeps it in `IntrepidManagerDB.facts`; `/reload`, then `tools/pull-results.sh`. The result is plain tables: read it to correct `tests/support/stock_templates.lua` and `tests/support/metrics.lua`, and to move names on the known-good list from `unverified` to `present`. The code is `IntrepidManager/ui/Demo.lua` and `ui/Facts.lua`; their tests run on the stand-ins, so what the game answers is what the run in the game is for.

## The message test (`/im msgtest`)

Raiders will run the addon, so responses, votes and tallies travel as addon messages, and what this server does with them was only known from another addon's notes. `/im msgtest run` (code: `IntrepidManager/net/MsgTest.lua`) is the measurement. Two clients in one group, both with the build: the one that types the command sends, the other only listens (it starts listening when the addon loads) and answers pings. The run is data, not code: a hello ping, probes of the message size (255 bytes and the sizes above it), then, on the group chat and again by whisper, pings (round trips), a burst of 10 messages of 100 bytes, 20 of the largest size, 40 of 60 bytes, 20 alternating between two prefixes, and 20 paced 0.5 and 0.25 seconds apart. About 3.5 minutes. Every send records the game's result code (`Success`, `AddonMessageThrottle`, `InvalidMessage`, ...), every arrival records when and in what order, and a message the server echoes back to its sender gives the delay on one clock. The record is `IntrepidManagerDB.msgtest` (runs with their sent rows, `received`, `replies`, `restrictions`); it contains no player names. Read both clients' files after a `/reload`.

The tests use two stand-in games joined to a fake server (`tests/support/fake_chat.lua`) whose delay, tick, per-tick cap, burst throttle (per client or per prefix), loss and reordering are knobs; it is a place to test a client's reaction, not a model of the real server.

## The loot test (`/im loot`)

`/im loot` (code: `IntrepidManager/game/LootWindow.lua`, a first slice of R3-5) is for a master looter with the loot window open. It lists the item slots and the candidates (numbers differ from group to group, so the player is always found again by name), `/im loot give <slot> <who>` gives one slot with `GiveMasterLoot`, and `/im loot sweep <who> [poor, common or uncommon]` gives every item up to that quality to one player, one at a time, each only after the game cleared the previous slot. `<who>` is a number from the list, a name (or the start of one), `me` or `other`. The game tells the loot master nothing when the receiver's bags are full, so "no answer in 2.5 seconds" is the sign and the sweep stops there. The record is `IntrepidManagerDB.loottest` (`gives`, `sweeps`: item ids, qualities, slot and candidate numbers, the events seen and when; no names). The tests use `tests/support/fake_loot.lua`, a fake master loot window that plays the answers seen on 2026-10-20.

## The council session (`/im session`, `/im respond`, `/im offers`)

Slice 1 of the council feature (code: `core/Council.lua` the rules, `net/CouncilWire.lua` the messages, `net/Outbox.lua` the sending, `game/Bags.lua` the bag list, `game/CouncilSession.lua` the client side). The loot master queues items that are already looted, either shift-clicked into `/im session add [item] [item]` or from `/im session bags` (bound items with the trade time left, and unbound items of Uncommon or better) with `/im session bag <numbers>`, then `/im session start [seconds]` (60 by default). Every client with the build gets the offer on the group chat, says hello by whisper, and answers each item with `/im respond <item> <bis, up, os or pass> [note]` until the timer runs out (the last answer counts); the loot master reads them in the chat and with `/im session results`. `/im session end` ends it early. The wire format is a TEST protocol (prefix `IMC1`; offer, answer, end, hello; at most 255 bytes, fields joined by `~`, never a pipe) that the ADDON-002/003 spec replaces or extends before votes and tallies. The sender queue keeps to what the game allows on a prefix (a burst of 10, then 1 a second; measured 2026-10-21) and holds sends during a boss fight. The record in `IntrepidManagerDB.council` has item ids, counts and timers only. Tests: `council_test`, `council_wire_test`, `outbox_test`, `bags_test` (pure), `council_session_test` (two stand-in games through `tests/support/fake_chat.lua`).

## The council windows (`/im session`, `/im offers`)

`ui/SessionPanel.lua` (the loot master's window: the queue, the timer, Start and End, the answers of the picked item), `ui/BagPicker.lua` (a clickable list of what the bags hold, with the box Include grays and whites) and `ui/ResponseFrame.lua` (the raider's answer frame: a row per item with its tooltip, the time left and the four buttons, and a note box) are view-model windows like the others: they show the model they are given (`masterModel()`, `rowsModel(n)`, `offerModel()` of `game/CouncilSession`) and call callbacks. The session tells them of changes through `session.hooks`, and the main file makes them on first use and opens the raider's frame when an offer arrives. They use the kit's new `clear` chrome (`kit.window({ chrome = "clear" })`: a translucent dark panel with a thin border, the way a loot council's windows look) and `kit.fit(text, width)`, which cuts a name with three dots to fit its box. Tests: `session_panel_test`, `bag_picker_test`, `response_frame_test` (each also checks the layout in every state and density with `tests/support/intact.lua`), and a whole-addon test in `toc_load_test`.

## Import the night, export the awards (`/im import`, `/im export`)

Build 0.0.17. `game/Exchange.lua` is the engine behind the two windows that were only samples before (`ui/ImportWindow`, `ui/ExportWindow`). **The night** (`IntrepidManagerDB.night`): what `ns.Night.read` accepted of the string (roster, bosses, priorities and `known` as the rows that passed, the raid, the phase, the time it was made and imported); a new import replaces it, a string that does not read or an open loot session keeps it. **The awards** (`IntrepidManagerDB.awards.log`, at most 2,000, with the names of the recipients because the Raid Desk needs them): `CouncilSession` tells the exchange when an item is awarded (`awarded`), taken back (`unawarded`) and given (`given`, with how: `trade`, or `manual` when the loot master keeps it or hands it to Disenchant or the guild bank). A record is `{ id, rev, session, at, date, phase, raid, itemId, item, toId, to, pseudo, decision = "council", priority, encounter, npcId, zoneId, delivery, status }` as in section 6.1; ids are `s-<start in base 36>-<4 random characters of this load>-<number>`, revisions `max(previous + 1, server time)`. Nothing is edited in place except `delivery` and `status`; a new recipient is a removal and a new award. The roster id is set when the recipient's full name matches exactly one roster entry of the night (spec section 2); the priority is the night's priority for the item, the one the recipient is on when there are several. The export (`exportModel`) uses `Awards.select`: with a night, the awards of its phase that its `known` list does not hold in that revision (counted as new or changed); with none, the last 14 days; or everything. It is written by `Awards.encode` and was read back by the Python reference reader (`tests/exchange_test.lua` runs `synthetic.py check` when Python is there). To rehearse: paste a night of the synthetic pack into `/im import`, run a session, `/im export`, copy the string and run `python3 tools/synthetic.py check --clipboard --expect awards --night night.txt`.

## Synthetic nights and awards (`tools/synthetic.py`)

Made-up raids for the copy-and-paste between the addon and the Raid Desk (the app's importer is LOOT-005 and does not exist yet). Everything is invented; the strings are written with the reference writer of `tools/exchange_fixtures.py`, so any reader that follows `docs/spec/exchange-v0.md` reads them.

- `python3 tools/synthetic.py night [--seed N] [--players 24] [--items 24] [--date YYYY-MM-DD] [--size 20] [--item-ids FILE] [--roster-json FILE] [--emulator] [--plain] [--out FILE]` makes a night string to paste into the addon's import box. The roster has awkward entries on purpose (no surname, one full name twice, an alt, letters outside ASCII); `--plain` leaves them out. `--item-ids` takes lines `itemId name` (for real beta items); `--roster-json` a roster of the app's test guild; `--emulator` gives the roster the ids `player-1`, `player-2`, ... of the Raid Desk's emulator seed.
- `python3 tools/synthetic.py awards --night FILE [--seed N] [--count 12] [--out FILE]` makes the awards string for a night: priority awards, two pseudo awards (disenchant, guild bank), two awards decided by roll or otherwise, some assigned and some received. Use it with the night string of a real test guild once the app can make one: the awards then carry that guild's roster ids and priority ids.
- `python3 tools/synthetic.py pack [--seed N] [--dir DIR]` writes a rehearsal folder: `night.txt`; `awards-01` to `awards-07` (the first export, the same again, a later one with changes and a removal, an older one, conflicts, a newer revision of an award edited in the app, a file with one row of every unusual kind, and two loot masters' strings pasted at once); `broken-*.txt` (checksum, truncated, a smart quote, the wrong box, a newer envelope, not ours) and `good-wrapped-by-chat.txt`; `states/` (what the app is assumed to hold before each paste); `expected.json` and `README.md`. The same seed and options give the same files.
- `python3 tools/synthetic.py check [FILE | -] [--clipboard] [--expect night|awards] [--night FILE] [--state FILE]` reads a pasted string (a night, or awards from the addon) and says what it holds, which rows have errors and why; with `--state` it prints the preview category of every award; with `--night` how many recipients and priorities are in that night. After a real session: copy the addon's export, run `check --clipboard`.
- `preview` is a reference for section 6.3 of the spec (Error, Conflict, Duplicate, Stale, Changed, Possible duplicate, Unmatched, New), driven by a small JSON of what the app holds. It is there to write the expected results and to give the app's importer something to be compared with; the app decides.
- `fixtures [--write]` keeps `docs/spec/fixtures/synthetic/` (a night, three awards strings, `expected.json`) up to date for the Lua tests (`tests/synthetic_test.lua`); `selftest` runs in CI.

The awards of a pack carry the roster ids and priority ids of the pack's own night. A real app only knows them if it was filled from the same data.

## Version check (`/im versions`, the Versions button)

Raiders will run the addon, so the loot master needs to see who has it and in which version (RCLootCouncil does the same). Two new messages of the council protocol (`net/CouncilWire.lua`, prefix `IMC1`): `V~1~version~class`, an announce on the group chat, and `Q~1~sid`, a full check on the group chat; the answer to both is the hello `K~1~sid~version~class` by whisper, with the session id `0` for an announce and the sid of the question for a check. Rules (`game/CouncilSession.lua`, the Versions section): a client announces itself once after it joins a group (`GROUP_ROSTER_UPDATE` or the end of a loading screen, three seconds later, at most once in 30 seconds; a boss fight holds it back and it is tried again 15 seconds later); a client that has a different version answers an announce with its own, once a minute per announcer, and a client with the same version stays quiet; a newer version than ours is told in the chat once per version and three times at most in a login; a full check makes everybody answer, and it forgets the earlier answers first so that a member who stays silent shows as "not installed" five seconds later. The hellos of a session are noted too. What is heard is kept in memory only (never in the saved variables); the saved record has the lines `announce`, `check` and `version` (the version heard, at most 40 lines) in `council.log`. Names are compared without a realm. `core/Version.lua` compares versions number by number. `ui/VersionWindow.lua` is a view-model window like the others (`versionsModel()` of the session, read every second while it is shown). Tests: `version_test` (the comparison), `version_check_test` (two to five stand-in games through the fake server), `version_window_test` (the window, with the layout check), and `toc_load_test` (the whole addon). A client on 0.0.14 or older does not know `V` and `Q` and shows as "not installed".

## Award first, then trade (`/im award`, `/im trade <name>`, the Award and Trade buttons)

Build 0.0.16. The loot owner's rule: the trade carries only what the raider won. `core/Council` keeps `winner` (the name the loot master awarded the item to; `award(n, who)`, `award(n, nil)` takes it back, refused before the start and after the item was given) and `given` (`give(n)`, once the trade went through) apart; `wonBy(name)` lists what a raider has won and not been given, `pending()` counts all such items. `game/CouncilSession` has `award`, `unaward`, `trade(name)` (all items of that winner, six at most per trade, through `game/Trade`), `owed()` (the list), the commands `/im award <n> <name>`, `/im award clear <n>` and `/im trade <name>`, and the models: `masterModel().items[].winner/given`, `.pending`, `.notice`, and `rowsModel(n)` rows with `winner` and `given` (a winner who did not answer is added as a row labeled "No answer"). The names are held in memory only; the record has `award`, `unaward` and `given` lines with the item number. The loot master's name is `(you)`: awarding to yourself and pressing Trade marks the item as given without a trade. New session on a closed session with awards that are not given yet warns first and drops them on a second press within 10 seconds (`/im session new` is the same); `/im session add` is refused over them.

`ui/SessionPanel` shows an Award button on every answer (until the item is given), and on the winner's row a highlight, Trade and an x; after the trade that row says "given" and the list says "given" (gold "won" before). Tests: `council_test`, `council_session_test` (the award and trade tests), `session_panel_test` (with the layout check on winner rows), and a whole-addon test in `toc_load_test` that awards from the chat, trades from the window's button and sees "given".

## Award by trade (`/im trade`, the Trade buttons)

`game/Trade.lua` gives an item by trade: it opens the trade window with a player (unless it is open), picks the item up from its bag slot, clicks the first EMPTY trade slot and reads the slot to see that it went in; the loot master and the raider press Trade themselves. The order matters: `ClickTradeButton` is a click on the slot, so on a slot that holds an item it takes the item back onto the cursor (seen on 2026-10-22), and on an empty slot with an item on the cursor it drops the item in. Every step, the events and the game's answers are kept in `IntrepidManagerDB.tradetest` (steps, events with times, the result word; no names), and the session notes the item as given when `UI_INFO_MESSAGE` says "Trade complete." (`ERR_TRADE_COMPLETE`). The raider is found by name among `party1` to `party4` or `raid1` up (`GetUnitName(unit, true)`, which gives "First Surname"). `tests/support/fake_trade.lua` is a fake trade window and bags that play this; its options make the window refuse, be too far away, block a call or ignore a click. Build 0.0.16 puts several items into one window (`give(list)`, six at most, 0.1 s apart, each from its own bag slot; an item that fails after others went in leaves them in and says so), reads the slots at every change and every accept and gives only the items that were in the window at the last accept (or, without the message, the ones whose id left the bags), and never uses an open window unless it is with the right player (`UnitName("npc")` or a window the addon opened itself). The real run of 2026-10-22 (build 0.0.15) showed the whole sequence: `TRADE_SHOW` 0.22 s after `InitiateTrade`, `TRADE_ACCEPT_UPDATE` with the flags `0,1` then `1,1` as the two players pressed Trade, and `TRADE_CLOSED` (twice) with the message "Trade complete." in the same instant. Build 0.0.15 adds: the cursor is cleared before the pickup, a bag slot that reports `isLocked` ends the run with "locked", and a trade is complete when the game says so or when fewer bag slots hold the item than before (the real run of 2026-10-22 saw `TRADE_CLOSED` but never the message); the run also keeps the first six `UI_INFO_MESSAGE` texts (the other player's name masked) and the flags of each `TRADE_ACCEPT_UPDATE`, and `completedBy` says which way the completion was seen.
