# Roadmap, decisions and work lanes

Last updated 2026-10-18. This file records direction, policy decisions, milestones and work lanes. [backlog.json](backlog.json) is the canonical item/status tracker; [the changelog](../CHANGELOG.md) records verified releases. Feature-status descriptions below provide context, not a second independent tracker. Keep them consistent with those files and follow [the maintenance rules](../CONTRIBUTING.md#backlog-patch-notes-and-publishing).

## Dates that drive the order

- **2026-11-04** WoW: Forever launch, not a full-app delivery deadline. High-priority adoption targets for launch are roster review of dashboard comments (`MEMBER-004`) and mobile usability, beginning with touch-accessible Casual/Hardcore help and an audit of other hover-only tooltips (`UX-002`). Roll out other core web-app functionality progressively between launch and December 9; roster, access, teams and calendar usability come first.
- **2026-12-09** the first raids unlock (Barrow Deeps 10, Hyjal Summit 20, Onyxia 40). Scheduled raids and sign-ups must be ready for members to use in advance of that night's raid, with the first immutable starting roster/sign-up snapshot taken at its scheduled start on December 9. These are firm requirements, not part of the optional delay.
- **First-raid loot, 2026-12-09:** target recording awards from the first raid without requiring priority listings. Use need-before-greed rolls until priorities are adopted. If app recording is not ready, leaders record loot in a spreadsheet and a later upload workflow preserves those awards; that upload is planned, not available today.
- **Around 2026-12-15:** begin using priority listings. Recording a receipt and deciding its recipient by priority are separate capabilities; recording must not require an active priority list.
- **2026-12-22:** target full rollout of all planned functionality, including loot audits, priorities, the production addon, Discord and advanced automation. These are targets, not claims of implementation. If everything is ready, the full rollout may start December 9; otherwise soft-open over the first one or two weeks of raiding. December 9 scheduling, sign-ups and the first snapshot do not slip with this broader rollout.
- **About 2026-10-21 and 22** the beta ends. Game data in the app (buffs, debuffs, scopes) must be re-checked then, in launch week, and on 12-09.

Core web-app functionality is what "most functionality" means for the November 4 to December 9 window; it excludes the addon, Discord and advanced automation. Those remain in the broader December 22 target. Targets do not override validation, authorization or immutable-history requirements; record and explicitly agree any change of scope or date rather than silently treating unfinished work as complete.

## Decisions

| Topic | Decision |
| --- | --- |
| Loot is editable | Guild Leaders and Raid Leaders can edit awards and priorities after the fact (people swap gear without telling officers). Every change is recorded in an append-only audit log (who, when, before and after, optional reason) that nobody can edit or delete from the app. The as-awarded snapshot (candidate order and council note at decision time) stays frozen inside each award. Awards are never deleted: "removing" one is an edit that marks it removed, with a reason. |
| Audit log visibility | Every guild member can read it. |
| Rules must enforce it | The audit entry is written in the same atomic batch as the change and the rules require it, so a modified browser cannot skip it. Rules tests (`npm run test:rules`) come with the change. |
| Old local-preview import | Never used. Delete the "Import local data" feature and the Guild Leader exception in the award rule, so there is one validated way to create an award. |
| Raids | Leaders can edit and cancel upcoming raids and correct the details of past ones (for example who actually showed up). Raids are never hard-deleted, and every change is audited. |
| Raid teams and scheduled raids | Target behavior: one scheduled raid night can include multiple zones, each with its own 10-, 20-, or 40-player size. The corresponding groups are included automatically: all four 10-player teams, both 20-player groups, or the single 40-player group. Assignments are live until the scheduled start time. A server-side job automatically locks a snapshot of assigned teams and sign-ups at the start; later changes to the Raid Teams tool do not change that raid. Guild and Raid Leaders may make audited changes to the locked raid team while it is in progress. Attendance is recorded against the raid snapshot. Scheduling/sign-ups are live, but automatic starting snapshots and in-raid roster corrections are not built yet; the first starting snapshot is required December 9. |
| Sign-up character | Members choose their linked main (the default) or a direct alt for each raid. One response per account: Accept, Tentative, Absent, Late, Bench (voluntary). Authenticated server callables enforce the start cutoff, cancellation and unavailable dates; direct writes are denied by Firestore rules. An overlapping unavailable event sets Absent and locks changes until all covering events are removed. Removing events retains Absent until the member explicitly chooses a new response. Leader benching and capacity decisions come later. The selected character uses its current Raid Teams assignment; the live preview is not a starting snapshot. |
| Raid zones | Leaders maintain the zone catalog and each zone's 10-, 20-, or 40-player size in Settings. They select one or more zones when scheduling a raid night; each selected zone snapshots its name and size so later catalog edits do not rewrite scheduled raids. |
| Raid notifications | Send reminders when a raid is created, 24 hours before, and 1 hour before. Delivery channel and server implementation are to be decided; scheduled server work is required for reliable timing and automatic roster locking. |
| Leavers | Agreed MEMBER-001 workflow: Guild Leaders remove/restore accounts, never themselves. Removal atomically sets role `Removed` and clears the reciprocal character link. Characters, assignments and history remain. Removed accounts cannot access guild data or raid callables, but may read their own access record and sign out; the Firebase Auth account is not disabled/deleted. Restoration grants Member access without a character link; any relinking or leadership promotion is a separate explicit action. Until deployed, use the manual unlink/demote/disable-Auth runbook; do not delete the member doc first. |
| Character identity and requests | Character document IDs are stable and must survive renames, spec changes and main/alt changes. Guild Leaders alone approve new-alt/link requests, class/spec changes, renames and promotion of an owned alt to main. An approved spec change applies its class/spec default raid role; retain the Guild Leader's manual role override, with no separate member role-change request. Main promotion moves the account link to the new main and makes the old main and its other alts direct alts of the new main, preserving all character IDs, team assignments and historical snapshots. MEMBER-002 implements member submission, withdrawal and private history on My dashboard, with reusable Guild Leader review controls initially in Member access. Existing-character alt requests require an unlinked character with no main, account pointer or alts of its own. Review notes are optional and visible to the requester. Approvals recheck ownership and refuse stale snapshots. MEMBER-003 follows, reusing the queue rather than rebuilding approval logic. See backlog for delivery state. |
| Leadership dashboard and raid readiness | Agreed MEMBER-003 scope: a separate Guild Leader-only Leadership tab, keeping My dashboard personal. Compact summary counts precede missing raid responses, character requests and coverage gaps. Readiness is per character, with mains and direct alts treated equally; members manage their own characters on My dashboard and Guild Leaders manage any character in the roster. Missing flags mean not ready. Any ready owned character qualifies its active linked account for one response check; an unready main does not exclude a ready alt. Readiness does not restrict sign-ups, grant access, assign teams or guarantee a raid spot. See the implementation acceptance scope below; not implemented by this documentation change. |
| Loot input | Paste an RCLootCouncil-format export (CSV) with a preview before anything is saved, plus manual entry. The format stays addon-agnostic because the guild may write its own addon. Item names and icons from Wowhead's unofficial tooltip endpoint are optional; manual entry must work without it. Warcraft Logs waits until it supports Forever. |
| Positional priority and filters | A player listed twice for an item: the first receipt satisfies the first listing, the second the second. Filters: slot, boss, only items with a priority, hide completed, player and class. Both are important. |
| Roles | **Guardian** is a Druid spec (feral tank, defaults to Tank) and **Feral** defaults to Melee. Done. A Guild Leader can set any character's role; the spec only supplies the default (done). Survival Hunter keeps Ranged as its default. |
| Alts | The roster holds one entry per character. An alt can be linked to a main (done: optional `mainId` on the roster entry, set in the Edit member dialog; the loot and attendance rules below are not built yet). For loot, alts are considered only after all mains, except in a run made up only of alts in 10 or 20 player content (to be recorded per raid). Attendance is per player, so linked alts roll up to the main. |
| Attendance | Rolling 3 months. Members see their own percentage, leaders see everyone's. Voluntary and involuntary benches are recorded as different things. Open: how each counts (see Open questions). |
| Discord | App sign-ups are live. Planned: an additional sign-up and notification channel through a guild-owned Discord bot and Cloud Functions, with no third-party raid tool. Target December 22; not a dependency for December 9 app sign-ups or starting snapshots. See Discord sign-ups below. |
| Member dashboard | A landing tab for signed-in members who have a linked character. It shows their characters (main and alts), raid sign-ups, raid team, loot priorities, loot and upcoming raids, in that order of importance. Members without a linked character still see the app and the tools they see today. Access stays guild members only; nothing is opened to the public. Leaders get extra Management tabs in the same app, not a separate dashboard, and can see what members see. See Member dashboard under Dependent work and rollout slices. |
| License | MIT for the code only. Crest and interface artwork were generated with ChatGPT; spec icons are Blizzard artwork from danetch/wowspecsemojis and stay non-commercial. |
| Readability | One CSS pass that raises small text sizes and contrast, after the leaders have seen screenshots. |
| Hosting plan | Production is on Blaze and Functions are deployed. Confirm a small budget alert is configured; enabling billing does not establish that the alert was set up. |
| Process | Node 24. Pull requests are merged with a merge commit. Rules changes come with rules tests. |

## Open questions

- **Bench counting.** Both kinds of bench were chosen to count as absence, and the two kinds must be told apart. Confirm whether an involuntary bench (the leader asked someone to sit) should also count against that player, or only be recorded.
- **Alt-only runs.** The exception to "mains first" needs a per-raid flag; confirm the wording and where it is set when raid sign-ups are built.
- **Fallback upload.** Agree the spreadsheet columns, recipient matching, duplicate detection and audit provenance before building the upload. Earlier spreadsheet awards must not appear as decisions made at upload time.
- **December 22 acceptance scope.** All planned features, including addon, Discord and advanced automation, are targeted. Turn research-stage extras into explicit acceptance criteria and dependencies; this target does not resolve open bench policy, addon messaging support or other feasibility questions.

## Work lanes

The point of the module layout (see `ARCHITECTURE.md`) is that several people can work at once. Lane A touches Firestore rules and shared files and is sequenced carefully; lane B is client-only feature work that does not wait for it.

### Order of work

- **Core rollout (11-04 to 12-09):** stabilize member access, roster/account links, raid teams, calendar and sign-ups. Guardian spec, editable role, alt links and audited raid edit/cancel are done. Coverage and the Removed status remain planned; they are not November 4 release gates.
- **Firm first-raid path (12-09):** prepare raids and collect sign-ups before the first raid; implement automatic immutable starting roster/sign-up snapshots for its scheduled start. Preserve that snapshot as the baseline for attendance even if reporting arrives later.
- **First-raid loot target (12-09):** prioritize safe manual award recording independent of priorities, stable recipient identity and the correction/audit path. Finish the audit foundation before relying on the app as the authoritative loot record. If not ready, use need-before-greed rolls and record receipts in a spreadsheet for later validated upload; do not invent priority snapshots for rolled awards.
- **Priority adoption (around 12-15):** roster-picked candidates, remaining priority/audit workflows and filters. Positional completion and encounter/player/class/completion filters are implemented; slot and "only items with a priority" filters remain planned.
- **Full rollout target (12-22):** complete the remaining planned raid/loot functions, audits, imports, addon, Discord, reminders, attendance reporting and advanced automation. Work may run in parallel when dependencies allow, but must not displace the firm December 9 snapshot path. A spreadsheet upload must preserve the original raid/award date and distinguish later entry from the original decision; its exact format is still to be designed.

### Lane A: foundation (rules, data model, shared files)

Dependency sequence, each as its own small pull request. Raid-start snapshot work is a parallel first-raid critical path, not blocked behind the entire loot sequence:

1. Rules tests and a CI job for them, tolerant reads and error boundaries, access-screen fixes, the dark-theme fix (pull requests being sent for review).
2. Fix: approving a join request must not overwrite an existing member (found by the rules tests; done in the join-request overwrite fix).
3. Audit-first loot: stage 1 rules support audited award edits and append-only audit entries. Remaining: audited client create/edit/remove and priority workflows, audit-log reader, tightened create/priority rules, and retirement of the local-preview import and Guild Leader award exception. Award-time snapshots remain immutable throughout. Update documentation with each implemented stage.
4. Pick candidates from the roster (stable roster ids) instead of typing names.
5. Phase, status, council status and team-name settings (10-, 20- and 40-player teams) (replaces the hardcoded "Launch prep" and "Preparing for launch"). Done: `settings/general`, the Guild Leader Settings tab and its rules tests.
6. Raid edit, cancel and correction, with audit entries. Done: leaders click a raid on the calendar to edit, cancel (reason required, raid stays visible as Cancelled) or restore it; the rules require a `raid_{id}_{rev}` audit entry in the same batch; tests in `tests/rules/raid-edits.test.ts`. Not built yet: a screen to read the audit log.
7. "Removed" status for leavers, with a no-access screen.

Lane A files: `firestore.rules`, `firebase.json`, `src/guildApi.ts`, `src/useGuildData.ts`, `src/useGuildSession.ts`, `src/features/loot/**` for the award and priority write paths.

### Lane B: feature modules (client-only, can start now)

Each is one feature folder plus the one-line registry or wiring change described in `ARCHITECTURE.md`. Client-only work needs no rules or Functions deployment but still needs a hosting release.

- **Raid coverage checklist** (very important): a panel showing which buffs and debuffs a 10, 20 or 40 player team covers and what is missing. A design exists; ask for it. All game facts live in one editable data file with a source and confidence for each entry.
- **Positional priority completion and loot filters**, in `src/features/loot/`: completion and encounter/player/class/hide-completed filters are done. Slot and "only items with a priority" remain planned. These read priorities and awards; they do not change how awards are written.
- **Guardian spec, editable role and alt link (all done)** in `src/features/roster/` and `src/shared/game/classes.ts`. The alt link is an optional field on the roster entry (roster rules do not validate fields, so no rules change).

### MEMBER-003: agreed implementation acceptance scope

Policy agreed 2026-10-18; implementation remains planned in the backlog.

- **Location and access:** a separate Leadership tab for Guild Leaders only, not Raid Leaders. My dashboard stays personal. Reuse the existing character-request queue and approval dialogs; do not add another approval system or broaden request-read permissions. Real membership and Firestore rules remain the authorization boundary; VIEW AS must never reach data hooks or write helpers.
- **Layout:** compact summary counts, then missing responses, character requests, and coverage gaps, in that order. Review character requests here; link to Calendar, Raid Teams, Member access and the roster for other workflows rather than duplicating their editors. Keep existing tools available.
- **Raid selection:** default to the next upcoming non-cancelled raid, with a selector for other upcoming non-cancelled raids. Distinguish no upcoming raid, loading, read failure and an empty result.
- **Readiness controls:** each character has an independent ready/not-ready flag tied to its immutable character identity. Mains and alts have equal standing; a rename or main promotion must not transfer or reset another character's flag. Members manage only their linked main and owned direct alts on My dashboard; Guild Leaders manage any character's flag in the roster. Raid Leaders receive no extra readiness-write authority from their role. Enforce ownership and allowed-field writes in the backend, with rules/server tests as appropriate.
- **Initial state and population:** no flag means not ready; do not bulk-mark existing characters ready. Count each active account with a reciprocal linked main once if any of its owned characters is ready. Identify it by its current main and list its ready characters beneath. A ready main does not make an unready alt ready, and a ready alt qualifies an account with an unready main. Unlinked or removed accounts do not become response obligations merely because a roster character is flagged.
- **Response interpretation:** any saved response counts as responded, including Absent and Bench. Accept, Tentative or Late using a character not marked ready produces a separate review warning, not a missing-response entry or a refused sign-up. Absent and Bench produce no readiness warning. Readiness never changes saved responses, unavailable-date enforcement, cancellation or start-cutoff behavior.
- **Honest empty states:** show excluded/not-ready and unlinked setup counts separately so zero missing responses cannot imply every member answered when nobody is marked ready. Do not label a sign-up or readiness flag as proof of attendance.
- **Coverage:** show gaps for teams/groups matching the selected raid's sizes, using current team assignments and links to the existing detail. Reuse shared coverage logic without feature-to-feature imports. Preserve provisional/unknown game-data warnings; do not present this as signup-adjusted coverage, confirmed attendance or an immutable starting snapshot.
- **Non-goals:** no reminders, automatic readiness checks, automatic benching/capacity decisions, raid-spot entitlement, attendance reporting, starting-snapshot implementation or automatic character-decision notifications in this slice.
- **Validation and release:** cover role/ownership boundaries, mixed ready/unready main/alt combinations, main promotion, one-account counting, each response state, excluded/setup counts and raid selection. Check light/dark and narrow layouts. Build, lint and unit tests must pass; rules changes require the full rules/server suite. Deploy any required backend/rules changes before the matching Hosting release, only on request. This work must not displace RAID-001's December 9 requirement.

### Discord sign-ups and notifications
- **Discord sign-ups and notifications (December 22 target).** Not started; needs raid edit and cancel (item 6, done) first. The bot is planned, but the exact reminder delivery behavior still needs agreement. In order:
  1. A Discord user ID on members, set by a Guild Leader in Member Access, so a sign-up maps to a roster character and its main.
  2. Announcements through a channel webhook (a Cloud Function) when a raid is scheduled, changed or cancelled. One-way.
  3. Sign-up buttons on a bot-posted message, mapped to the app's existing response states and character choices. Discord calls an HTTPS interactions endpoint (a Cloud Function) that verifies Discord's request signature and the member's identity, character ownership, cancellation, unavailable dates and start-time cutoff, writes the same `raids/<raidId>/signups/<uid>` document, and updates the message. Direct client writes are denied; Discord must reuse the server-side authorization and availability transaction serialization, not bypass the existing callable guarantees.
  4. Reminders at raid creation, 24 hours before and 1 hour before, from scheduled server work; attendance rolls up to the main.
  - Needs: production Blaze/Functions are available, but Discord and scheduled reminders are not implemented. Configure Cloud Scheduler as needed; keep the bot token and webhook URL in function secrets, never in the repo or client; configure the Discord public key server-side. A Discord server admin must create the application and invite the bot with narrow permissions (post and edit messages in one channel); each function needs server-side authorization.
  - Open: whether sign-ups made in the app should also update the Discord message (two-way), and how a sign-up counts toward the coverage checklist.

## How to avoid stepping on each other

- Changes to the shared files listed in `AGENTS.md` get their own commit and a note in the pull request.
- If you touch `firestore.rules`, add or update the matching test in `tests/rules/` and run `npm run test:rules`.
- One format-everything commit is deferred: it conflicts with every open branch, so it only makes sense when no branch is open.
- Say in the pull request which lane an item belongs to, so two people do not start the same thing.
